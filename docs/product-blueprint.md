# 安糖心语（GlucoMind）· 产品蓝图

> 用途：把「东一榔头西一棒槌」的需求收成一条主线，明确每个功能为什么做、做到什么程度、什么时候做、什么时候不做。
> 范围：患者端（App）为主；医护端由另一位同学负责，本文只写接口边界。
> 版本：2026-10-23 第一版。

---

## 一、一句话定位

**给 1 型糖尿病、且对低血糖有强烈恐惧（FoH）的人，一个不会用「再测一次」来安抚他的陪伴工具。**

不是血糖仪表盘（那是硅基、Glooko 的事），不是病历系统（那是 Tidepool、医院 HIS 的事），而是**恐惧与行为的干预层**：识别「他为什么反复查」「他为什么不敢运动」「他为什么补碳水补过头」，然后在当轮对话里给出具体、可执行、不加重焦虑的回应。

这句话同时是需求闸门：**一个功能如果不能让上面这条链路更准、更快、更安全，就不做。**

---

## 二、现实盘点：论文写了什么，我们做到了什么

技术栈：PostgreSQL（SQL，SQLAlchemy 2 异步 + Alembic 迁移）+ FastAPI + React Native（Expo）。

| 论文 Fig 1 / 正文的能力 | 现状 | 卡在哪 |
|---|---|---|
| Multimodal sensing：CGM、可穿戴、饮食图像、对话、纵向行为 | 手环观测（导出文件）、对话、手工血糖、行为记录可用；**CGM 只有图片入口，没有解析器**；饮食图像未做 | 数据源拿不到（厂商不开放）+ 解析器没写 |
| Patient digital twin（来源、时间、置信度、有效期） | 信念/行为事件带原话与出现方式；量表带版本与时间；血糖带情境；语音听感带置信度与 10 分钟有效期 | 监测类数据（CGM）缺失，导致 twin 只有「说的话」没有「测的数」 |
| Multi-agent（七类专门 agent） | 三个角色：对话主 Agent、健康档案管理、主动关怀；安全约束由程序执行 | 有意的架构简化（见第五节） |
| Event-driven proactive care（预测低血糖、运动风险、反复补碳水） | 日常问候、约定回访、心率异常候选；24 小时低血糖复盘已接线待重构 | 预测类触发依赖 CGM；目前只有「文字提醒」，没有饮食/运动/用药的具体指导 |
| Mobile prototype | 聊天、记录、健康档案、沟通方式量表、行为与信念、设置与更新 | 完成度最高的部分 |

**一个必须承认的落差**：论文写的「多模态感知 + 多 Agent 协同」在论文里是架构主张，落到实现时，**大部分模态的瓶颈不是软件写得慢，而是数据进不来**（CGM 要授权、饮食要靠人拍、运动要靠手环导出、用药要靠医院或患者手记）。所以蓝图的顺序必须是「先把能进来的数据接好，再谈推理」。

## 三、需求闸门：四个问题

任何新需求（包括老师提的）先过这四条，缺一条就先不做：

1. **它服务 FoH 闭环的哪一步？**（识别 / 应对 / 复盘 / 长期改变）
2. **数据从哪来？**（患者自己输入、厂家导出、设备广播、公开数据集；没有合法稳定的来源就先不做）
3. **错了会怎样？**（医疗类：剂量、诊断、急救——必须有确定边界，不能让模型自由发挥）
4. **患者能不能删？**（不能撤回的个人数据不入库）

## 四、三层能力模型

把现有与计划中的功能放进三层，避免「每加一个功能就多一个页面」：

### 第 1 层：记录（数据进来）
- 血糖（已有）：点测，来源区分指尖血 / 扫描 / 传感器 / 化验单 / 报告导入；测量时间与录入时间分开。
- CGM（P0）：文件导入（CSV/PDF）→ 确定性解析 → 预览确认 → 入库；不承诺实时。
- 用药/胰岛素（P1）：类型、剂量、时间、备注；**只记录，不给剂量建议**。
- 饮食（P1）：餐次、碳水量（估）、照片（可选）；不做营养成分库的完整版。
- 手环观测（已有）：心率、步数、睡眠、血氧（导出文件）；实时心率已通（BLE 广播）。
- 行为与信念（已有）：从对话抽取，带原话与出现方式，可删。

### 第 2 层：理解（状态与风险）
- 健康档案（已有）：权威事实。
- 量表档位（已有）：恐惧 × 感知 → 四象限 → 每周联系频率。
- 摘要与趋势（已有）：近 7 天血糖摘要、行为提及摘要。
- **事件级双风险（P1，创新点）**：把「生理风险」与「感知风险」在**同一时刻**分开标注（比如血糖 4.2 但患者主观恐慌 vs 血糖 3.1 患者毫无感觉），驱动不同的回应策略。论文 §2.3 有这个概念，但没有落到事件级实现——这是我们可以先做的。
- 用药/饮食对血糖的影响（P2）：只在有足够配对数据后做，先做相关性提示，不做因果结论。

### 第 3 层：干预（怎么回应）
- 当轮对话策略（已有，本周加固）：拒绝把测量当安抚、过度补碳水定量、否认核对、家人归因。
- 主动关怀（已有）：日常问候、约定回访、心率异常候选；24 小时复盘（下周重构）。
- 风险升级（已有）：剂量类问题不给数字、症状加重建议联系医生/急救。
- 转介与教育（P2）：把「该找医生」的时机与话术模板化。

## 五、四个不变量（架构级，不可妥协）

1. **数据最少够用**：模型只拿它这一轮需要的结构化摘要，不给整份病历、不给原始聊天全文。
2. **结论可追溯**：任何进入回答的数值都必须带来源（手输/设备/报告）、时间与置信度；知识类回答必须带出处。
3. **安全边界确定**：谁能看谁的档案、什么情况必须升级、剂量类问题怎么答——由程序判定，不交给模型。
4. **患者可删可撤回**：单条可删、授权可撤销、注销即删除；软撤回只用于「需要时间线语义」的数据（血糖），行为与信念是硬删除。

## 六、与论文的差距：哪些补、哪些改成 limitation

**补**（能落地、有数据源）：
- CGM 文件导入与解析（P0）
- 用药/胰岛素记录（P1）
- 饮食记录（P1，最小形态）
- 事件级双风险识别（P1，创新点）
- 主动关怀从纯文字扩展到「带具体做法的行动建议」（P2）

**改成 limitation**（不硬补）：
- 实时 CGM 抓取（授权 + 稳定性双雷；改成合作方接入或 future work）
- 饮食图像识别（需要标注数据与模型评估，Companion 论文阶段不做）
- 七 Agent 协同（见下）
- 正式 FoH 量表（等 HFS-II 授权；现在是自编六题 + 自我感知题）
- 临床级评估（没有患者队列，只做技术验证与红队）

**为什么不做七个 Agent**（也是写给导师看的答案）：
七类分工在论文里是理想化描述。实现时我们把「安全边界」与「状态权威」从 agent 里拿了出来：前者变成程序化约束（权限、剂量、升级路径），后者变成 patient twin（带来源的状态集合）。用 agent 承担这两件事，等于把「确定」换成「概率」；再叠一个「患者 Agent」，同一份状态会出现两个写入者。等 twin 的字段补齐（尤其 CGM）、并且需要「并行评估多个假设」时，再拆 agent 才有意义。

## 七、导航与交互：加功能不等于加图标

现状风险：血糖、CGM、饮食、用药、运动、报告、手环、量表、行为记录……如果每个都上侧边栏，患者会找不到「今天该干什么」。

**改法：三级结构**

| 层级 | 内容 | 原则 |
|---|---|---|
| 首页（对话） | 今天该做的事：未完成的约定、最近一次低血糖复盘、最近血糖、一条主动关怀 | 只放「今天相关的」，不放全部功能 |
| 记录（一个入口，五个页签） | 血糖 / CGM / 饮食 / 用药 / 手环 | 同类聚合，新增一类只加一个页签 |
| 我的 | 健康档案、沟通方式量表、医护授权、隐私与数据（删除/撤回）、设置与更新 | 低频但重要，集中放 |

侧边栏只保留：对话、记录、我的、医护授权（如果已授权）——不超过 5 项。

## 八、上下文预算：功能越多，模型越不能全看

这是最容易被忽略、也最容易把产品拖死的部分。做法是**三层上下文**，而不是把聊天记录越堆越长：

| 层 | 内容 | 预算 |
|---|---|---|
| 状态层（结构化） | 档案摘要、近 7 天血糖摘要、量表档位、行为/信念 top-k、当前关怀任务、未完成约定 | 约 2k–4k token |
| 检索层（工具） | 历史消息搜索、血糖区间查询、知识库引用、量表历史 | 按需调用，每次结果 ≤ 1k token |
| 窗口层（原文） | 最近 N 轮原文 + 结构化摘要接力（已有压缩机制） | 约 4k–6k token |

三条硬规则：
1. 任何新功能的数据，先问「这一轮真的需要吗」，需要才进状态层；
2. 需要历史的，一律走工具查询，不塞进提示词；
3. 指标只看三个：首字延迟、上下文 token、回答里的数值/引用准确率。

## 九、路线图

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0（1–2 周）** | 血糖来源与补录字段；CGM 文件导入（解析 → 预览 → 入库 → 对话引用）；数据契约文档 | 导入一份真实导出文件，数值与时间正确、可删、对话能引用 |
| **P1（3–4 周）** | 用药/胰岛素记录（只记录）；饮食记录（最小）；记录聚合页与导航重构；事件级双风险标注 | 新功能不增加侧边栏项；上下文 token 不超预算 |
| **P2（论文/创新）** | 行为-信念图驱动的干预选择；双风险识别的小规模评估；主动关怀从文字到行动建议 | 有可复现的评估脚本与数据 |

**明确不做**：实时 CGM 抓取（插件/逆向）、自动给药建议、任何诊断性表述、全量表体系、把七个 Agent 硬凑出来。

## 十、差异化：我们能比市面产品好在哪里

市面上的主流产品（mySugr、Glooko、Tidepool、硅基/三诺等）在「数据记录与呈现」上都很成熟，我们不可能在这条赛道上赢。**能赢的地方只有三个，而且都不靠功能数量**：

1. **FoH 行为环**：把「反复查血糖」「回避运动」「睡前加餐」「否认恐惧」当成可识别、可回应的行为模式，而不是当成数据质量噪声。竞品记录次数，我们处理「为什么反复查」。
2. **可追溯与安全约束**：数值带来源、回答带出处、剂量类问题不给数字、拒绝时给替代方案。这在医疗产品里是硬门槛，多数对话式健康产品做不到。
3. **评估骨架**：12 场景 × 3 轮的红队评测 + 真实患者故障复盘 + 提示词改动的性质标注（改行为 vs 改评分）。这是能写进论文、也能说服审稿人的东西。

**关于「做软件是不是互相抄袭」**：大多数软件产品都是重组已有能力，差别不在点子，而在**选谁的问题、守什么边界、能不能证明有效**。我们的选择是：只服务 1 型 + FoH 这个窄人群，把边界写进代码，用评测证明没有退步。窄，但站得住。

## 十一、与其它工作的边界

- 医护端（另一同学负责）：我们提供接口——患者授权后可按时间窗读血糖、手环、量表分数与象限；我们不做医护工作台的 UI。
- 论文：本文与 `docs/glucose-data-format.md`（数据契约）共同构成「实现说明书」，用于回答「论文的架构在代码里长什么样」。
- 评测：`api/evals/simulated_patient/` 的红队套件为所有对话策略改动的回归门槛。
